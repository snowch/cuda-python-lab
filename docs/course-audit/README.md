# Independent audit of CUDA Python Lab

**Fix experiment state before expanding the course.** All 38 starters produced the right shapes and values in the real browser simulator. Following the exercises in order exposed a different problem. After removing a stencil halo load, switching to the next case produced 19 where the starter gives 27. In softmax, the next case inherited the unstable formula and produced NaNs. Restoring the starter fixed both. In a separate two-tab experiment, saving a prediction in another lesson made earlier work disappear from the durable course state.

The course already gives a Python reader something substantial to learn from: a complete editable host program and kernel, local compilation, inspectable PTX, offline execution, captioned examples and a path to native profiling. Its strongest teaching sequence asks for a prediction that distinguishes two mechanisms, then makes a small edit with an observable consequence. Its weakest asks the learner to infer hardware behavior from two identical output arrays without a way to examine the difference. Preserve the workbench. Make the state, question and evidence of each experiment explicit.

## Assessment from five perspectives

**Python learner.** Starting at one host value and one thread works. The independent host-initializer edit produced device result 73 and host input 5, a concrete test of understanding. Keep Show main() and Show target line. At coalescing, the learner must combine row-major offsets, 2D coordinates, warp order and sectors at once. Teach one row and one address group before applying the transpose. For matrix multiplication, require one complete dot product before two shared tiles.

**CUDA programmer.** The simulator runs complete host code and compiled kernels. The independent NumPy checks include rectangular transposes, matrix multiplication and stable softmax. Make supported launch shapes explicit: the reduction halves a power-of-two width within 32 slots, scan uses a single block, and transpose maps x before y. Preserve data-race and barrier questions about permitted outcomes. Four runs using plain histogram increments all yielded 2 in the contested bin; a result of 32 on another schedule would not demonstrate race freedom. The browser PTX targets sm_70 through a compatibility compiler; the separate native cross-check targeted sm_80. Neither measures a physical device.

**GPU architecture instructor.** The learner encounters address sectors, barriers, warp masks and occupancy but rarely follows one operation from Python through allocation, scheduling, execution and return. Bring the locator forward before each new mechanism. Thread ownership is logical. Resource allocation constrains residency; dependencies constrain eligibility; issue width, pipeline availability and memory can constrain progress. CUDA address spaces, cache policies, and physical DRAM topology need separate explanations. Teach counterexamples to occupancy-as-speed and sector-count-as-DRAM-bytes. A broader architecture course also needs SIMD/SIMT comparison, graphics versus compute, memory ordering, cache/coherence and interconnect trade-offs; name vendor- and generation-specific assumptions.

**UX and accessibility reviewer.** The themes maintain a consistent reading order and the content column and title wrap on narrow screens. Run, Stop and the Console have clear text. Keyboard access to the editor, downloads and recordings works in Chromium. The phone captures show the apparatus for running code and the request to the learner separated by an editor-height scroll. Use a task-specific short prompt at the control, keep full code collapsible by learner choice and provide local scrolling alternatives. No automated contrast failure in the tested closed states establishes conformance for overlays, focus or all syntax tokens.

**Instructional designer.** The existing predict–run–explain sequence is a sound foundation. Teach the distinction between “my code ran”, “my output matches the selected reference”, and “my explanation predicts the next case”. Vary one cause at a time. Ask the learner to construct an input that refutes a mistaken generalization, such as “the last block always has idle threads”. Give hints in three levels (concept, pseudocode, worked answer), record help used separately from success, and retain a free-form workspace. A 10/10 claim requires observed independent transfer and accessibility sign-off.

## Comparison with external curricula

The CUDA 12.6.3 programming guide treats the hierarchy of threads, memory hierarchy, synchronization and heterogeneous execution as a connected programming model. Its hardware multithreading and performance sections connect residency to latency hiding, memory transactions and instruction issue. Here direct code coverage is strong for block-local algorithms, atomics and bounds, partial for memory hierarchy and divergent execution, and thin for multi-block cooperation, warp collectives, ordering/scope and asynchronous dependencies. Teach one correct multi-launch global reduction before cooperative groups. Document the support boundary of each Python binding and toolkit version. [CUDA C++ Programming Guide 12.6.3](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-c-programming-guide/index.html)

NVIDIA’s APOD cycle (Assess, Parallelize, Optimize, Deploy) and distinction between requested and actual bandwidth give the missing performance spine. Nsight Compute separates scheduler statistics, warp state, occupancy, instruction mix and memory workload. The affine/transpose/fusion appendix already asks appropriate questions. Promote its methodology: establish correctness, time a defined interval with warmup and repeated samples, predict a limiting resource, inspect a timeline or counter, change one variable, retest at another size. Include a case where an optimization loses. [Best Practices Guide 12.6.3](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-c-best-practices-guide/index.html) · [Nsight Compute 2024.3 profiling guide](https://docs.nvidia.com/nsight-compute/2024.3/ProfilingGuide/index.html)

Stanford CS149 Fall 2024 places GPU architecture and CUDA programming alongside data-parallel thinking, programming specialized hardware, memory coherence and workload decomposition. Its treatment of map, reduce and scan points to a missing transfer task here: ask the learner to select the primitive and partition the work before seeing a kernel. Use the GPU route to investigate why the same algorithm performs differently under different memory systems. Add optional comparisons with AMD wavefronts and Intel subgroups using actual vendor-specific execution widths and tools; reserve graphics stages and distributed consistency for an explicitly broader track. [Stanford CS149, Fall 2024](https://gfxcourses.stanford.edu/cs149/fall24)

**CUDA Python breadth.** The named native route is Numba-CUDA-MLIR 0.6.0 with CUDA 12. The browser is a separate frontend/runtime subset. The investigation archive introduces PyTorch interoperation, streams, pinned host buffers and zero-copy views. Add a versioned support table for Numba-CUDA, Numba-CUDA-MLIR, cuda-python driver/runtime bindings, CuPy and PyTorch, with a small demonstration of ownership, lifetime and stream interoperability. Include library baselines before custom kernels. Survey graphs, managed memory, virtual memory, IPC, cooperative launch, clusters and architecture-specific asynchronous operations; use native-only or reading paths where unavailable. A complete NVIDIA compute foundation and broad GPU computer architecture are distinct curricular targets.
