# Shared workbench revision

At a portrait-tablet width of 820 CSS pixels, the previous workbench gave the vector-add task 240 pixels and the Python editor 462 pixels. A learner had to read the task in a narrow strip beside the code, encounter much of it again under Run, then scroll past the Console to find the model. The new sequence gives the task 725 pixels and the editor 752 pixels. The model appears immediately after the lesson introduction. The returning learner can skip directly to the experiment. [Owner’s Android Chrome feedback](https://github.com/snowch/cuda-python-lab/issues/51#issuecomment-7240880267) · [Independent review](https://github.com/snowch/cuda-python-lab/pull/52#issuecomment-7241000299) · [Vector-add editor before and after](comparisons/vector-add-820x1180-light-edit.jpg)

## Choosing the layout

I used the repository’s **Frontend Design** guidance to assess the complete reading surface, including how much space is left for code and whether a secondary action competes visually with Run. I used **Instructional Design** to trace one learner action to the next, using the open program, a prediction and an observable result. The owner’s physical-device report motivated the correction. The comparison images here come from Chromium. [Frontend Design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) · [Instructional Design](https://github.com/joelrkohlman/instructional-design/blob/main/SKILL.md)

Before changing the implementation, I rendered two alternatives over the same build for first-value, vector-add and softmax. Both placed the model before the workbench and used a single reading column at 820 px. The first stacked code and Console at every width. The second paired them on wide screens. At 1440 px the paired prototype gave code 653 px and Console 342 px, versus 996 px of usable code width when stacked. The empty Console occupied space throughout the first read of the program, then had too little width for an array or a long diagnostic. I chose the stacked version for all three lessons. Short related choices and array cells can still sit side by side when they fit. [Rendered alternatives](comparisons/prototypes.jpg) · [All 24 prototype captures](captures/prototypes.zip) · [Measurements](logs/prototypes.json) · [Reproduce the prototypes](prototypes.mjs)

The final design separates prose and code through typography and spacing. The editor and printed output retain their dark code surfaces. The surrounding instructions and controls use the page theme. The main header scrolls with the lesson so that it cannot obscure controls while reading or resizing. The model, task, prediction, editor and result follow the same order visually and by keyboard. One Console action returns focus to the original prediction field, which retains its answer and current source-bound question. “Task” and “Revisit” return to the actual selector and model. A starter-specific question in a lesson without a source model is labelled as such.

“Prepare starting program” and “Review undo preparation” disclose the affected source and kernel ownership alongside the action that would replace them. Opening the disclosure cannot change learner work. Warnings about a failed save, a newer saved program or a recovery copy remain available beside Run. The answer field grows with a short paragraph and remains resizable for longer notes. The exercise retains one active instruction. A separate evidence cue appears when it adds something to inspect. The portrait reading flow keeps long softmax expressions together and leaves space for a long answer without creating an empty neighboring column. On a phone, long Python lines still scroll inside the editor. The full-page comparison also shows the tradeoff. On modeled lessons, the editor starts farther down because the learner first encounters the model. The introduction’s shortcut and each model’s “Show source” control support a direct route to the experiment. At desktop size, the short prose uses a comfortable line length and the editor can use the full content width.

## Reproduce the visual review

Build each revision in a clean separate worktree with `npm ci && npm run build`. The baseline for this layout comparison is `72158a9c4195747db9e3bf1f4101d7034f38bec9`, before the owner correction. The verified revised application is `f61ec9f3574104546bea8180fb2193e8e02b3b82`. The later evidence-only commit changes the build’s displayed revision. Run the following scripts from the checkout containing this directory. Use the commands in the original package for the additional simulator and offline replays. [Original reproduction commands](../README.md#reproduction-and-limits)

```sh
node docs/testing/issue-51/workbench/prototypes.mjs /path/to/before/dist /tmp/prototypes
node docs/testing/issue-51/workbench/capture.mjs /path/to/before/dist /tmp/before
node docs/testing/issue-51/workbench/capture.mjs /path/to/revised/dist /tmp/after
AXE_PATH=/path/to/axe.min.js node docs/testing/issue-51/workbench/resize.mjs /path/to/revised/dist /tmp/resize
```

The Playwright runs used Chromium 156.0.8078.79 and reduced motion. The native zoom settings used full Chromium 159.0.8154.6. `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` can select the installed Chromium and `ZOOM_CHROMIUM` can select the full browser separately. Axe-core was 4.14.1. These checks cover Chromium emulation and keyboard/touch input. Physical Android hardware, screen-reader speech, human audio listening, native GPU execution and uncoached learner testing were outside this verification. GPT-6.2 Astra with High reasoning was requested. The session provided no independent runtime readout of the model or effort.
